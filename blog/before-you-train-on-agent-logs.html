Getting your agent's logs ready for post-training

October 2026

A team has months of logs of its AI agent at work and wants to post-train on them, by fine-tuning or RL. I built Trace Check-up to help, starting from the logs alone: can a training environment and a reward be built from these recordings; what data to collect next; and roughly what each post-training method can reach. Checking, after training, whether a claimed improvement is real is coming soon.

How you use it

Drop in the logs you already have: OpenAI chat transcripts, OpenTelemetry GenAI traces, Arize Phoenix span tables, ToolTalk or ATIF trajectories, or a spreadsheet with one tool call per row. Emails, most card numbers and phone numbers written in common ways are hidden as soon as the log is read; names and addresses are not. It runs on your own computer, where nothing is sent anywhere (Trace Check-up). The code is published when the first team asks for it; until then, the example report shows what it writes.

A minute later you get two pages. The first is for the people who run the agent: it opens with one verdict — “Check the made-up IDs before training the AI”, or “Trying again already works well” — and then the checks behind it, in plain words. The second is for the engineer, with every number, the rule that produced it and the files it was read from. Another agent can ask the same questions through MCP.

The mistakes it checks for

Each check looks for a mistake that is easy to make and expensive to find late:

  • A corpus with many empty episodes can look fine by row count.
  • Many training tasks can have no demonstration at all.
  • Evaluation can render prompts differently from training.
  • A fine-tuning gain can come only from the tasks the model trained on, when nothing is evaluated on held-out tasks.
  • Most of the tokens a fine-tuning loss is computed on may not be actions.
  • Final states a simulator produces can be rejected by the real scorer.
  • Checkpoints can be picked by a validation loss computed on a different random sample each time.

None of these needs a GPU to find. Each is a count over the logs, the configuration or the evaluation files, and each blocks a specific next step until it is fixed.

Seven stages, each with gates

The report reads the corpus in seven stages — intake, corpus health, coverage, environment fidelity, learnability, training health, outcome. Each stage has metrics, gates that say what they block, and actions computed by rules over the metrics. It is read-only (every input file is hashed before and after), runs on a CPU, and makes no API calls. The output is a JSON document with the hash of every file it read, so anyone can later ask whether a saved report still describes the data and the code.

When outcomes are too sparse, compare the steps

One question is whether a simulator behaves like the real system, task by task; if it does not, RL in the simulator teaches the wrong thing. The obvious test compares success rates of the same policy in both environments. It mostly cannot decide: with 8 runs on each side, a task needs at least 5 successful runs before any arrangement of them could be significant, and most tasks never succeed at all.

So the report compares steps instead. It replays the saved trajectories through both environments and, for each task, counts the tool calls one environment ran and the other refused (an exact paired test, corrected for the number of tasks). Because each task has many calls, this test can decide tasks that the success-rate test leaves undecided. Each disagreement also says why — an argument the real tool does not accept, a refusal the simulator has no check for, a state the real scorer will not read — which points at the file where the fix belongs.

Forecasts that admit what they do not know

The report says what each method — fine-tuning, rejection sampling, RL in the simulator, test-time methods — might reach, always as a range and never as a single number, with a tag saying whether it was measured, extrapolated or taken from published work. An end that cannot be estimated is drawn as unknown, never as zero.

The page for the people who run the agent goes further: no sentence on it is written by hand or by a model. Each one is a phrase with numbers from their log filled in, chosen by written rules whose limits they can see and change. And their report never carries my project's conclusions: a customer is owed readings of their own files.

The comparison I have not seen anyone make

Platforms that check a training run compare the trained model with the one in production. I have not found one that compares it with the untrained agent simply trying again at the same cost — and sometimes retrying is the cheaper fix. Today the page shows two cards side by side: if the agent tries again, measured on the customer's own log (tasks done after one try and after k tries, and what the extra tries cost), and if you train a small model now, a rough estimate from published results, marked low-reliability because those results go both ways — on the same ~2,000 starting examples, one study's 8B model got worse while its 14B model got better. Measuring the comparison directly, from a log before training and a log after, at the same spend, is the next piece; it is coming soon.

Limits: the checks were built on one project's own logs; another team's logs will break assumptions mine did not. The forecasts from published work are deliberately labelled low-reliability.
